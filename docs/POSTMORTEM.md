# 缺陷复盘：从「看着像」到「算得出」

> 这份文档记录首版交付后被指出的三类问题 —— **穿模、管线安装不合理、动力链断裂** ——
> 以及它们背后真正的原因。目的不是道歉，而是把每一类错误翻译成一条**可执行的机制**，
> 让同一类错误在结构上不能再发生。
>
> 所有数字都来自本仓库可复现的运行输出（`npm run lint:geom` / `npm run test:core`）。

---

## 0. 一句话结论

首版的问题不是「零件画少了」或「不够仔细」，而是：

> **跨构件的空间关系没有真值表，几何正确性没有可执行的判据，验收依赖人眼看截图。**

三者叠加，等价于「用肉眼看二维投影，去验证三维约束」。这在构件数超过约 50 件后必然失守。

## 1. 缺陷 A · 接缝无人负责（动力链断裂 1.8 m）

**现象**：燃气轮机输出 → 减速齿轮箱 → 轴系 之间出现 1.8 m 的悬空断口。
齿轮箱悬在半空，与燃机输出轴、与艉轴都不接触。

**直接原因**：`gt-output-shaft`、`gt-gearbox`、`gt-clutch` 三个构件的 `pos`
是在各自的局部坐标系里按「看起来大概在这个位置」估出来的（`[-4, 6.9, -1.9]` 一类），
而燃机输出法兰与艉轴法兰分别由另外两个文件里的常量决定。三处数字从未对齐。

**真正的原因**：**接缝不属于任何构建者。**
`gasturbine.js` 只对燃机负责，`shafting.js` 只对轴系负责，中间那段"谁都不属于"。
在分文件、分构件生成的流程里，跨文件的空间接缝天然没有 owner。

**修复**：把传动链提升为**单一真值表** `src/core/driveline.js`：

```js
export const NODES = {
  'pt-flange':    { p: [-4.0, 8.3, -1.90], a: [0, 0, 1],  r: 0.30, label: '动力涡轮输出轴端法兰' },
  'angle-top-in': { p: [-4.0, 8.3, -1.55], a: [0, 0, 1],  r: 0.28, label: '上直角传动箱输入法兰' },
  ...
};
export const SEGMENTS = [
  { id: 'gt-flex', from: 'pt-flange', to: 'angle-top-in', kind: 'flex', parts: ['gt-flex-coupling'] },
  { id: 'gt-angle-drive', from: 'angle-top-in', to: 'angle-top-out', kind: 'gear', parts: ['gt-angle-drive'] },
  { id: 'gt-drop-shaft', from: 'angle-top-out', to: 'angle-bot-in', kind: 'shaft',
    parts: ['gt-drop-shaft'], supports: ['gt-drop-shaft-bearing'] },
  ...
];
```

几何一律**由节点坐标反推**，而不是各写一份。例如动力涡轮输出轴的局部 z 直接由节点算：

```js
const zEnd = NODES['pt-flange'].p[2] - (-3.35);   // 构件原点到法兰面的距离
```

**防复发机制（结构性的，不靠自觉）**：

1. 链图连通性自检 `checkChain()`：除两端自由端外每个节点度数必须为 2；
   不允许孤立节点、悬空支路、不可达段；`shaft` 段两端轴线必须与该段方向共线（cos ≥ 0.999）。
2. 审计器反向校验：沿每段中心线取 15 个采样点，要求 `SEGMENTS[i].parts` 声明的构件
   几何确实覆盖这些点（容差 0.12 m）。**"表里有、几何没有" 会直接报错。**
3. 节点吻合度：每个节点要求两侧构件各有一件几何落在节点半径内。

```
=== 链图 ===
{"ok":true,"issues":[],"segments":7,"nodes":8}
传动链空洞 0 · 节点失配 0
```

## 2. 缺陷 B · 穿模（6 类，全部是「朝向」与「空间预算」错误）

| # | 现象 | 直接原因 | 属于哪一类 |
|---|---|---|---|
| B1 | 飞轮包围盒 3.1×3.1×3.0，报告与曲轴重叠 1.66 m（盘厚仅 0.34 m，物理不可能） | 轮缘用 `torus`（默认位于 XY 平面、轴向 z）后**多写了一行** `rim.rotation.x = π/2`，把轮缘立成垂直于盘面的竖环 | 朝向：默认轴向 vs 意图轴向 |
| B2 | 缸盖变成一块**竖立圆盘**，顶面的示功阀、螺栓圈全部悬在盘外，排气支管必然从盖体内部穿出 | 缸盖是回转体，`lathe`（轴 = y）被写成 `latheZ`（轴 = z） | 同上；且被**六缸全量复制** |
| B3 | 控制台宽 2.6 m 沿 x 布置，直接穿出 x = 6.42 的舷侧板 | 布置尺寸按"舱内可用宽度"取，没有和舷侧板坐标对账 | 空间预算缺失 |
| B4 | 行车吊钩 y = 7.2，插进排气集管（y ≈ 7.5） | 吊钩高度按"看起来够高"取 | 空间预算缺失 |
| B5 | 左舷后通风筒（x = −5.2）穿过燃气轮机燃烧室机匣（x ∈ [−5.18, −2.82]）与隔声罩 | 通风筒位置早于燃机布置确定，燃机后来"长"到了它身上 | 空间预算缺失 |
| B6 | Kort 导管支撑臂（定子）z = 0.4，插进桨叶（桨叶轴向包络 ±0.35） | 定子与桨叶的轴向间隙没有显式分配 | 空间预算缺失 |
| B7 | 海底门在 z = −14.1，距桨盘 1.1 m，落在 φ6.9 m 桨叶回转包络内 | 同上 | 空间预算缺失 |

**关键观察**：B1、B2 是同一个错误的两个实例 —— **回转体的默认轴向与意图轴向不一致，
靠"记得加一行旋转"来纠正**。这种写法一旦写错，会被循环复制到全部同类构件
（6 个缸盖 = 6 处同样的错）。

**修复方式必须区分两类**：

- **朝向类** → 改成「由轴线参数生成」而不是「生成后补旋转」。
  缸盖改用 `lathe`（轴 = y，与缸套同轴），轮缘删掉那行多写的 `rotation.x`。
- **空间预算类** → 建立「占位 → 审计 → 让位」的闭环，把冲突暴露成数字而不是眼睛。
  B3～B7 全部由 `geom-lint` 报出后逐个让位，并留下注释说明"为什么在这个坐标"。

## 3. 缺陷 C · 管线安装不合理（spaghetti 管系）

**现象**：五组管系（燃油 / 滑油 / 海水 / 压缩空气 / 电缆）由 `CatmullRomCurve3`
穿过几个手写点生成 —— 斜向走管、无支吊架、无法兰、直接穿过设备、
`aux-pipe-fuel` 的竖管从凸轮轴大齿轮中间穿过去。

**原因**：把"管子"当成"一条曲线"，而不是"符合管装规范的构件"。
曲线穿过手写点时，**没有人检查它中间经过了什么**。

**修复**：管路即数据。`src/assemblies/piping.js` 把每根管子写成
「正交折线 + 管径 + 材质 + 支吊架间距」：

- 只允许 x / y / z 三轴走向，转角按管径生成圆滑弯头（`bend = max(0.12, r·2.2)`）；
- 直段每 ≤2.2 m 一个 U 形管夹 + 立杆 + 底板，每 6 m 与两端设法兰；
- 管系与它服务的设备**共用配置标签**（燃油 / 滑油 / 启动空气 `diesel-only`），
  柴油机构型下不会被留在舱里对着空气供油。

**审计判据**：对每根管的每个顶点，检查是否深入其他**块体设备**实体 18 cm 以上。
骨架/格栅类（平台、隔声罩、行车、桥架、栏杆）与管对管**排除** ——
镂空结构的 AABB 没有实体含义，管道交叉在 AABB 下无法与平行区分。

## 4. 缺陷 D · 同一规则写两遍（可见性漂移）

`PartRegistry.refreshVisibility()` 与 `auditScene()` 各自实现了一遍「当前构型下哪些构件可见」。
两次实现必然漂移，后果是审计拿**本构型下根本不存在的构件**去报缺陷：

```
=== diesel / cpp ===
  ⚠ gt-drop-shaft 段长 4.74 m → 无支承      ← 燃气轮机整机在柴油机构型下是隐藏的
```

**修复**：抽出唯一判据 `partVisible(part, state)`（`src/core/registry.js`），
渲染层与审计层都调它；传动链与支承检查再按「本构型下真实存在的段」裁剪（`liveSegments`）。

## 5. 缺陷 E · 审计不可复现

审计直接读「仿真此刻恰好跑到哪一帧」的位姿。连杆摆角、桨叶方位角、螺距都在动，
于是**同一个模型两次跑出的干涉清单不同**，报告无法作为门禁。

**第一版修复（不完整）**：`sim.setReferencePose(crankDeg = 0)` 保存并重置角度状态，
以 `dt = 0` 走一遍运动学。角度钉住了，但漏了 `state.pitch` —— 它是阻尼收敛量
（`damp(pitch, pitchTarget, 1.4, dt)`），页面跑了多久就收敛到哪。它不是角度，是**状态**。

**CI 把它抓出来了**：本地四构型 0 干涉，首次 CI 却在 `diesel/cpp` 报出 4 处
`cpp-blade-1..4 × cpp-crank-ring`（各 0.007 m³，ratio 0.234）。两边代码相同，
差别只在软件光栅与本地 GPU 的页面加载耗时 → `pitch` 收敛程度不同 →
桨叶转角 `(pitch/100)×0.56` 与曲柄销环转角 `(pitch/100)×0.56×0.55` 的相对位姿不同。
这条恰好证伪了「本地跑一遍就算验收」，也证明了门禁必须放在另一台机器上跑。

**最终修复**：`setReferencePose(crankDeg = 0, pitch = 0)` 把 `pitch` / `pitchDeg` 一起
保存、钉死、恢复；`quality.yml` 增加 `concurrency` 组，避免同一分支的并发 run 互相污染页面状态。

**实测证据**（页面加载后等待不同时间再审计，`diesel/cpp`）：

| 等待 | 审计前 `pitch` | 干涉 | 走管 | 链空洞 | 节点 | 已登记接触 | 审计后 `pitch` |
|---|---:|---:|---:|---:|---:|---:|---:|
| 200 ms | 59.296 | 0 | 0 | 0 | 0 | 38 | 59.296 |
| 1200 ms | 27.946 | 0 | 0 | 0 | 0 | 38 | 27.946 |
| 3500 ms | 22.262 | 0 | 0 | 0 | 0 | 38 | 22.262 |

`pitch` 相差近 3 倍，报告逐项一致；审计后状态原样恢复，不污染运行中的仿真。

**可迁移的规则**：确定性验收要钉的是**所有会随时间演化的状态量**，不只是几何角度。
凡由 `damp()` / 积分器 / 动画时钟驱动的量，都必须进参考位姿快照。

### 5.1 同一病根的第二处：验收把 wall-clock 当成仿真时间

几何门禁在 CI 转绿后，同一条流水线上的**交互回归却报 32/37**——本地是 37/37。
失败的全是「等 N 毫秒，再断言状态推进了多少」的项：

| 断言 | CI 实测 | 判据 |
|---|---|---|
| 继续后进度恢复推进 | 0.2170 → 0.2340（+0.017） | 要求 > +0.02 |
| 反向播放使进度回退 | 0.2340 → 0.2255（−0.0085） | 要求 < −0.02 |
| 燃机启动时序推进 | 9 次采样全是 `1:0.25` | 要求 step 与转速都涨 |
| 单缸熄火燃烧下降 | 0.00 → 0.32 | 要求 after ≤ before |
| 气流粒子淡入 / 淡出 | 开启 0.36 / 关闭 0.23 | 要求开启 > 0.5 |

根因不在功能：**主循环用 `Math.min(0.05, clock.getDelta())` 防止切标签页后的大跳**
（这个设计是对的，不该改）。但 CI 是软件光栅、帧率极低，每帧真实间隔几百毫秒却只算
50 ms —— 700 ms wall-clock 里仿真时间只推进约 0.05–0.15 s。于是 `explode.rate = 0.17/s`
只走了 0.017，燃机 `GT_STEPS[1].dur = 2.6 s` 的时序一步都没迈过去，燃烧脉冲也采不到峰值。

**换句话说：这些测试把「跑测试的机器有多快」写成了隐含前提。** 与缺陷 E 是同一个病根，
只是 E 发生在「几何位姿」，这一处发生在「时间基准」。

**最终修复**：给 app 增加 `stepWorld(dt = 0.05, frames = 1)` —— 只推进
`sim / explode / section / flow` 的状态、不渲染；回归测试改用它推进**固定帧数**
（例如 `stepWorld(0.05, 14)` ≡ 0.70 s 仿真时间），`test-core.cjs` 的第 6、7 节与燃机
时序 / 单缸熄火 / 粒子淡出、`test-dist.cjs` 的播放 / 反向，共 5 组等待型断言改为确定性
步进，并把每组收进**单次 `evaluate`**，让同步执行期间 rAF 无法插入。
（`test-dist.cjs` 是第三轮 CI 才暴露的最后一处：软件光栅下 `moving` 只到 0.017，
判据要求 > 0.05。）正常运行时 `animate` 仍按真实 dt 驱动，生产行为完全不变。

**实测**（改动后本地 37/37）：燃机时序 `1:0.31 → 4:0.43「高压涡轮自持」`、
熄火后燃烧强度归零、粒子 `0.972 → 0.018`、重装配 `0.864 → 0.660`。

为让「确定性」不是一句口号，把这 6 项断言收进**单次 `evaluate`**（同步执行期间 rAF 没有
插入机会），再分别在「主循环正常」与「`requestAnimationFrame` 完全停摆」两种页面下
跑同一序列，得到逐位相同的七组数值（`IDENTICAL true`）：

| 条件 | explode pp1 / pp2 / pp3 / pp4 | 粒子 on / off | 燃机末态 |
|---|---|---|---|
| rAF 正常 | 0.353 / 0.353 / 0.472 / 0.353 | 0.971853 / 0.017507 | `4:0.432` |
| rAF 停摆 | 0.353 / 0.353 / 0.472 / 0.353 | 0.971853 / 0.017507 | `4:0.432` |

这条实证已固化为 `npm run test:determinism`（`scripts/test-determinism.mjs`），接入 CI 的
独立步骤：任一组数值漂移即 `exit 1`。**验收的时间基准由被验证的仿真时钟提供，
而不是墙上的钟。**

**可迁移的规则**：凡断言「某状态在一段时间内推进了多少」，必须由显式步进驱动固定
仿真时间；`waitForTimeout` 只能用于等待渲染 / UI 稳定，不能充当时间尺。
本仓库仍保留若干此类等待（拖拽、缩放、选中后的稳定采样），它们不断言推进量，
但属于同一技术债，已在 `docs/SKILLS-RETRO.md` 登记为后续迁移项。

## 6. 缺陷 F · 审计精度与渲染合批互相牵制

`bakeStatic` 早期按材质把整件几何并成一个网格 —— draw call 是省了，
但整个构件被压成一个巨型 AABB，审计再也分不清「管子穿机器」与「管子贴着机器绕过去」。
首版审计因此报出 574 处干涉，其中绝大部分是这个原因造成的假阳性。

第一次修法：按 1.6 m 空间网格分块合批 —— 精度回来了，代价是 draw call 从 ~900 涨到 **2628**。

第二次修法（当前）：把两件事**解耦**。
合批前把每个实体子网格的包围盒留档到 `group.userData.solidBoxes`（构件局部坐标），
审计改用留档盒（随 `matrixWorld` 变换），渲染合批粒度与审计精度彻底无关。
分块尺寸放大到 5 m 后实测：

| 指标 | 按材质全合批 | 1.6 m 分块 | 5 m 分块 + 留档盒（当前） |
|---|---|---|---|
| draw call | ~900 | 2628 | **1982** |
| 审计精度 | 整件 AABB（不可用） | 子网格 | **子网格（不变）** |
| 干涉数 | 574（假阳性为主） | 50 | **0** |

## 7. 缺陷 G · 靠肉眼验收

以上所有缺陷的共同放大器：**没有一条可执行的判据**。
`README` 里写「已检查无穿模」，本质是「我看了几张截图」。

截图是二维投影，恰好被遮挡、恰好从正确角度拍的错误，**在截图里不存在**。
而且人眼对 0.2 m 级的穿模在 20 m 场景里几乎没有分辨率。

**修复**：把「正确」翻译成 5 类几何谓词，写成一个能退出非零码的命令行门禁：

| 谓词 | 判据 | 阈值 |
|---|---|---|
| 干涉 | 子网格 × 子网格 AABB 交集体积 / 较小件体积 | ≥ 0.04 且 ≥ 0.006 m³ |
| 走管 | 管壁顶点落入块体设备实体的深度 | ≥ 0.18 m |
| 传动链 | 段中心线采样点是否被实现件几何覆盖 | 15 点全覆盖，容差 0.12 m |
| 节点吻合 | 节点两侧构件几何到节点的距离 | ≤ max(0.25, r·1.2) |
| 长跨支承 | 声明支承件到轴线的垂距与轴向投影 | 垂距 < 0.9 m，落在段内 |

```bash
npm run lint:geom        # 四种构型全绿才返回 0
```

当前结果：

```
=== diesel / cpp · 可见 156/186 ===   干涉 0 · 走管异常 0 · 传动链空洞 0 · 节点失配 0 · 链图 OK
=== diesel / fpp · 可见 147/186 ===   干涉 0 · 走管异常 0 · 传动链空洞 0 · 节点失配 0 · 链图 OK
=== gas / cpp   · 可见  80/186 ===   干涉 0 · 走管异常 0 · 传动链空洞 0 · 节点失配 0 · 链图 OK
=== gas / fpp   · 可见  71/186 ===   干涉 0 · 走管异常 0 · 传动链空洞 0 · 节点失配 0 · 链图 OK
门禁：链图 PASS · 构型 4/4 PASS（干涉上限 0）
```

## 8. 豁免表：为什么不用「调大阈值」

机械配合在几何上**必然重叠**：轴穿轴承、叶根坐入桨毂、螺栓穿法兰。
如果为了消掉这些报告去调大阈值，真正的 0.3 m 穿模也会一起被放过。

所以 `src/core/audit-allow.js` **逐条登记**允许的装配接触，每条都写工程理由，
并且**双向匹配**（A×B 与 B×A 都命中）：

```js
{ a: 'shaft-intermediate', b: 'stern-shaft',
  reason: '中间轴后端法兰与艉轴前端法兰以螺栓对接（法兰止口互相嵌入）' },
{ a: 'gt-hp-casing', b: 'gt-hp-rotor',
  reason: '高压转子装于高压机匣内（叶尖间隙不计入几何模型）' },
```
