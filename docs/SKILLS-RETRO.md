# 为什么 AI 会稳定地产出「看着对、其实错」的成果

> 这篇不复盘某个模型，而是复盘**一类协作结构**。
> 触发点是本仓库首版被指出的穿模、管系不合理、动力链断裂 —— 但结论与 3D 无关。
> 同样的失效在长文档、大表格、多模块代码、汇报 PPT 里一模一样地发生。
>
> 目标：找出「为什么会需要二次返工」的机制，并给出可以写进 Skill 的硬规则。

---

## 1. 先承认一个事实

那些错误**不是随机失误**，也不是「模型不够聪明」。它们是可预测的、成体系的：

- 飞轮轮缘和缸盖犯的是**同一个错**（回转体默认轴向 ≠ 意图轴向）；
- 六缸的缸盖错法完全一致 —— 说明错误被**结构化复制**；
- 动力链断在「两个文件之间」而不是文件内部 —— 说明错误集中在**没有 owner 的接缝**；
- 管系斜穿设备，但每一根管子单独看都"起终点对"—— 说明校验粒度停在**端点**，没到**路径**。

可预测 = 可治理。下面是六个具体机制。

---

## 2. 六个失效机制

### M1 · 知识不是约束：提示词级的提醒会在长链生成中必然衰减

Skill 里写「注意不要穿模」「注意管路要规范」，这是**知识**。
知识进入上下文后，在几十个构件、上千行几何的生成过程中，被稀释成一句背景音。

> 软约束的通过率与生成链长度成反比。链越长，越接近「没写」。

真正的约束必须满足三条：**可执行、可判定、可退出非零码**。

本仓库的对照：

| 写法 | 类型 | 效果 |
|---|---|---|
| 「注意不要穿模」 | 知识 | 574 处干涉，靠肉眼没发现 |
| `PENETRATE = 0.18` + 顶点入体判定 + `exit 1` | 约束 | 0 处，且能防回归 |

### M2 · 局部正确 + 全局无人负责

生成是**按模块推进**的：一个文件、一个总成、一个函数。
每个模块内部自洽，模块之间的接缝**不属于任何一次生成**。

> 「接缝」是 AI 协作里最危险的位置：它在每一次局部生成里都刚好不在视野内。

本仓库 1.8 m 的传动链断口，正好落在 `gasturbine.js` 与 `shafting.js` 之间。
没有哪个文件"写错了"，但整体是错的。

**判据**：如果一个量需要两个模块共同保证，它一定会漂移 —— 除非它被放在**第三方**（真值表 / 接口契约）里。

### M3 · 反馈通道带宽不足：截图是二维投影

「看一眼截图确认一下」是 AI 协作里最常见的验收动作，也是最不可靠的。

- 截图有**遮挡**：错误藏在背面、藏在构件内部、藏在另一个构件后面；
- 截图有**角度**：换一个机位，穿模消失或出现；
- 截图有**分辨率**：φ20 m 的机舱里，0.2 m 的穿模约占 1% 画面宽度 —— 人眼与模型都看不出；
- 截图**不可比较**：没有基线，无法判断"这次比上次好还是坏"。

> 用二维投影验证三维约束，信息论上就不成立。

### M4 · 隐性默认值 + 结构化复制

`lathe` 的轴是 Y，`torus` 位于 XY 平面。这是库的默认值，不是意图。
写成「先生成、再补一行 `rotation.x = π/2`」时，**朝向信息存在人的记忆里，不在代码里**。

一次记错，就被 `for` 循环复制到全部同类构件（6 个缸盖 = 6 份同样的错），
而且因为"六个都一样"，视觉上反而显得**一致、可信**。

**修复方向**：把朝向变成**参数**（`axis: 'y'`），让错误无法表达；
而不是把朝向变成**补丁**（生成后再旋转），让错误只是"这次没想起来"。

### M5 · 数量型 KPI 挤压空间预算

「构件越多、细节越足越专业」是这类任务的隐含目标。
构件数量上去之后，**空间预算没有同步建立**：没有一张全局的占位表说明
「机舱左右舷走廊各留 1.2 m」「燃机机匣外径 ≤ φ2.4 且 x ∈ [−5.2, −2.8]」。

于是每个新构件按"我放在这里挺合适"落位，冲突只在**局部**判断 ——
而局部永远看不出全局冲突。通风筒穿燃机、海底门落在桨盘包络、控制台穿舷板，
都是这个机制。

### M6 · 没有可重放的验收基线

一次性验证通过 ≠ 每次通过。改动之后不重跑，错误会以另一种形式回来。

> 本仓库首版 README 里写着「已检查无穿模」。它不是谎言 ——
> 是**当时确实看了几张图**，然后这个结论被永久写进了文档。

没有基线，验收结论无法证伪，也就无法积累。

## 3. 返工为什么会发生：一个够用的公式

把上面六条压成一个粗糙但有用的判断：

```
返工概率 ≈ 1 − (可执行判据覆盖率 × 结果可复现率)
```

- **可执行判据覆盖率**：有多少条"正确性要求"被翻译成了能自动判定的谓词？
  本仓库首版 ≈ 0.05（只有 37 条交互断言，几何类 0 条）。现在是 5 类几何谓词全覆盖。
- **结果可复现率**：同一个输入重复跑，结论是否一致？
  首版审计读的是"仿真此刻跑到哪一帧"，复现率接近 0。现在钉死参考位姿，复现率 1。

两项都低，返工几乎是必然 —— 与"这次有没有被要求返工"无关，只是早晚。

## 4. 四条可迁移的硬规则

> 这四条与领域无关。写 3D、写文档、做表格、写后端服务，都适用。

### R1 · 单一真值表（Single Source of Truth）

任何**需要两处以上共同保证**的量，必须提到第三方并被双方引用。

- 3D：节点坐标表 → 所有传动构件由表反推
- 文档：术语表 / 数据来源表 → 正文与图表都引用它
- 代码：接口契约 / schema → 前后端都从它生成

**检验方法**：把同一份数据改一次，看要改几个文件。> 1 就有漂移风险。

### R2 · 审计优先（Audit-first）

先写**检查器**，再写被检查的东西。顺序反了，检查器就会去迁就已有实现。

- 3D：先定义「干涉 / 走管 / 链连续 / 节点吻合 / 长跨支承」五个谓词，再摆构件
- 文档：先定义「每条结论必须有来源、每个数字必须有口径」，再动笔
- 代码：先写测试的断言，再写实现

### R3 · 豁免表可审计，不许调阈值

允许的例外必须**逐条登记 + 注明理由 + 双向匹配**。
一旦允许「调大阈值让它别报了」，判别力就被一次性卖掉了，而且没人记得卖过。

判据：**说不出工程理由的重叠，就是缺陷。**

### R4 · 确定性验收（Deterministic Gate）

验收结果必须可重放、可比较、可退出非零码，能挂进 CI。

- 钉死随机源与位姿（本仓库：`setReferencePose(0)`）
- 输出结构化结果（JSON）而不是"看起来没问题"
- `exit 1` 卡住构建，而不是写进 README 的"已检查"

## 5. 这套东西应该怎么写进 Skill

现有 Skill 的形态大多是**知识包**：讲清概念、给出范式、列出注意事项。
对「生成」类任务，这个形态不够 —— 因为生成物的正确性不在知识里，在**产物内部的一致性**里。

建议每个生成类 Skill 都附带四件套：

| 组件 | 作用 | 本仓库对应 |
|---|---|---|
| **真值表模板** | 让跨模块的量只有一个来源 | `src/core/driveline.js` |
| **审计脚本骨架** | 把「正确」变成可执行谓词 | `src/core/audit.js` |
| **门禁命令** | 一条命令、非零退出、可挂 CI | `npm run lint:geom` |
| **豁免表格式** | 让例外显式、可审计、可复核 | `src/core/audit-allow.js` |

一旦这四件套存在，Skill 的角色就从「提醒你别犯错」变成
**「让你无法交付一个错误的东西」** —— 后者才是可复用的。

## 6. 一个反直觉的结论

首版并不是"偷懒"：它交付了 179 个构件、37 项交互断言、920 kB 单文件、
完整的测试日志和已知限制清单。工作量是真实的。

**但它把全部工程预算花在了「生成」上，几乎没有花在「校验」上。**

> 在这类任务里，**校验才是主体工程，生成只是素材准备。**

把这条想清楚之后，本轮的改动重心就很自然了：
新增的代码里，审计器（`audit.js` + `driveline.js` + `audit-allow.js` + `geom-lint.mjs`）
比新增的几何构件更值得写 —— 因为几何只解决这一次，审计解决之后的每一次。

## 7. 适用范围（不止 3D）

| 场景 | 典型的「接缝无人负责」 | 对应的 R1 真值表 |
|---|---|---|
| 多章节长文档 | 第 3 章的结论与第 7 章的数字对不上 | 数据 / 术语 / 结论登记表 |
| 多表联动 Excel | 汇总表口径与明细表不一致 | 指标口径表 + 命名区域 |
| 前后端联调 | 字段名 / 可空性 / 单位不一致 | OpenAPI / schema |
| 汇报 PPT | 正文说 3 个方向，附录列了 4 个 | 大纲 → 页 → 论点的映射表 |
| 多文件重构 | 改了 A 忘了 B 的镜像逻辑 | 单一实现 + 引用 |

判断标准始终是同一条：

> **这个量，是不是需要两个地方同时说对？如果是，它就必须只有一个出处。**
